Story

Maturin began as a paper habit-tracker: a single sheet split between a daily habit checklist and a sleep log. The system worked, but the format didn't — filling it out each morning took just enough time, at just the wrong moment, that it was reliably skipped.

Maturin rebuilds that system digitally, extended into a full project-management tool: daily tasks and habits alongside multi-person projects with real governance, reasoned about the way an actual team would — who's allowed to change what, what happens when they disagree, and what the real trend line looks like once it's measured rather than guessed. The hardest part of development wasn't the interface — it was preserving genuine day-to-day usability through the transition to digital while treating account security as non-negotiable: fully isolated per-user data, and deliberate handling of edge cases around account creation to prevent any leakage between users.

This is an active solo project, not a finished product. Automated test coverage is the one piece known to still be missing, and is the current focus.

Technical Highlights
  • 01Diff-based change approval. Designed a field-level, diff-based change-approval workflow: edits from contributors without sign-off rights are diffed field-by-field and routed as a pending change to someone with approval authority — the same pattern behind PR review or Google Docs suggestions, built from scratch for this domain.
  • 023-tier RBAC. Gated all workflow actions behind a viewer/contributor/owner permission system, so only authorized reviewers can approve in-flight changes.
  • 03Dependency-graph engine. Built cycle-aware phase locking using BFS traversal and topological ordering, preventing circular prerequisites from silently corrupting a project's timeline — rendered live via React Flow.
  • 04Request-time derived analytics. Implemented a weighted project-health score and a velocity-based completion forecast, computed live rather than cached, plus a suggestion engine that flags stalled tasks, abandoned habits, and slipping milestones.
  • 05Token-based auth. Built with bcrypt(12) hashing and 256-bit crypto-random single-use tokens, with an enumeration-safe reset endpoint that prevents account existence from leaking through timing or error messages.
  • 06Single-service authorization layer. Architected the backend so permission and approval logic lives entirely in one service layer, not scattered across routes or the frontend — 51 endpoints across 9 resource domains, all deciding "who's allowed to do what" in exactly one place.
